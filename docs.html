How AXELR AI actually works

No marketing haze, no fabricated endpoints. This page describes the pipeline that runs on every request, the three workspaces, the differentiators that aren't just rebranded ChatGPT, and the honest limits of each tier.

01 — Under the hood

How Axelr Actually Works #

Every request flows through the same pipeline. The order matters — semantic caching runs before memory recall, and memory recall runs before any provider is contacted. That is why repeat prompts return in ~14 ms without ever touching a language model.

text · request lifecycle
request
  │
  ├─▶ sanitize_input → detect_manipulation → contains_explicit
  │     └─ rejected → { success: false, provider: "security" }
  │
  ├─▶ semantic cache lookup
  │     key = workspace : task_type : prompt : (last 2 turns) : context_hash
  │     └─ HIT → return in ~14 ms (provider="semantic_cache")
  │
  ├─▶ context assembly
  │     ├─ conversation memory recall
  │     ├─ workspace addenda (per-workspace system prompt)
  │     └─ schema discovery (CSV/XLSX headers injected as context)
  │
  ├─▶ provider cascade  (ranked by circuit-breaker state + tier allow-list)
  │     ├─ primary provider gets a 400 ms TTFT threshold
  │     └─ sequential fallback chain: 0.5 s → 1.0 s → 2.0 s (jittered)
  │           └─ success → sanitize_ai_output → semantic cache write → return
  │
  ├─▶ local Twin Engine (hot-swap, offline inference)
  │     └─ success → return (provider="local_hot_swap")
  │
  └─▶ stub fallback (marked "[stub]" — never a fabricated answer)
        └─ return (provider="local_stub")
info
Providers currently wired: Groq, Google Gemini, Cloudflare Workers AI, OpenRouter, Mistral, HuggingFace, GitHub Models, NRouter, TextCortex. Order is re-ranked at runtime from per-provider latency percentiles stored in Redis.

Circuit breakers, not retry storms

  • Every provider and every (provider, model) pair has an independent circuit breaker.
  • Rate-limit failures (HTTP 429 / 402) open the breaker for 30 minutes.
  • Ordinary failures open it for 60 seconds after 3 consecutive errors.
  • Winners are always the least-recently-failed, not the least-recently-used.
02 — Workspaces

The 3 Workspaces #

A workspace is not a skin. It changes the system prompt, the default task type, the file types allowed, the provider allow-list for free/pro tiers, and the daily quota. Auto-detection exists — if you upload a CSV in Core, Axelr will offer to switch to Data. You can also lock the workspace in Settings.

comparison
workspace   task_type        accepts                       default endpoint
─────────   ──────────────   ───────────────────────────   ─────────────────
data        "extraction"     .csv .xls .xlsx .pdf          /api/extract
                             .png .jpg .txt .doc(x)

design      "frontend"       .html .css .js .ts .jsx       /api/extract
                             .py .go .rs .md .svg
                             .png .jpg (mockups)

core        "structuring"    anything (small text)         /api/extract
                             .txt .md

What changes per workspace

  • System prompt — Data gets an analyst prompt; Design gets a senior frontend engineer prompt; Core gets a generalist prompt.
  • Temperature & max_tokens — pulled from WORKSPACE_LLM_CONFIG; Data runs cooler, Design runs warmer.
  • Critic pass — code-bearing responses go through code_guard; if syntax or score fails, self_healer re-rolls once.
  • Structured output — Data responses can emit [JSON-DATA]…[/JSON-DATA] blocks that the UI renders as a table/chart and offers as CSV download.
03 — Differentiators

Features That Don't Exist Elsewhere #

1. AHE — Anti-Hallucination Engine

When structured extraction is required, AHE produces a deterministic verifier DAG over the retrieved fields. If a field can't be proven from the source, it's returned as null with a reason — never invented. AHE errors serialise as { code, doc_id, field, reason }, not as a 500.

2. Context-aware semantic cache

Most caches key on the raw prompt. Ours keys on workspace : task_type : prompt : last-2-turns : context_hash. The same question asked after a different conversation will not hit the cache, because the meaning of the question changed. That's why we can cache aggressively without returning stale answers.

3. Touch-Fix

Paste an error message next to a generated code block and the TouchFixEngine returns a patched version. It re-runs the same prompt that produced the code, injects the error as context, and passes the result back through the critic pass before returning. If the fix doesn't compile, it's marked as failed — not silently shipped.

warning
Not on this list: the public webhook API. It exists internally (core/webhook_pipeline.py mounts at startup when available) but is not a stable public contract. There is no API key system, no rate-limit SLA, no versioning promise. We're not going to write docs for something we can't support.

05 — Comparison

Why Axelr vs ChatGPT #

1. Multi-provider cascade, not a single backend

ChatGPT serves from one backend. Axelr routes across nine+ providers with per-provider and per-(provider, model) circuit breakers. When Groq gets rate-limited, Gemini is already warm. When Gemini errors, OpenRouter is next. A single provider outage never becomes a full product outage.

2. Local Twin Engine fallback

When every remote provider is down — all breakers open, keys missing, or TTFT thresholds tripped — Axelr can still answer. The Twin Engine runs local inference on the same host. If the engine isn't loaded either, the pipeline returns a stub with a [stub] marker. It will never fabricate an answer. You always know whether you got a real response or a degraded one.

3. Workspace-specialised prompts and task types

A Data request is task_type="extraction" with an analyst system prompt and a critic pass that verifies extracted fields. A Design request is task_type="frontend" with a senior-engineer prompt, code_guard syntax scanning, and an optional self_healer re-roll. There is no generic "assistant" mode that glosses over the task.

06 — FAQ

Frequently Asked Questions #

Do you offer a public API?

Not yet. Internally the routers exist (api/routes_core.py, api/routes_agents.py, api/routes_billing.py, api/routes_admin.py) and a webhook pipeline mounts at startup when available. But there is no public API key system, no published rate-limit SLA, and no versioning guarantee.

We're not going to publish fake docs for something you can't call. When a public API ships, this page will say so and there will be a real reference for it.

Why do I have to pick a workspace?

Because each workspace changes real behaviour: the system prompt, the default task_type, the file types accepted, the provider allow-list for your tier, and the daily quota counters.

Auto-detection exists — upload a CSV in Core and Axelr will offer to switch you to Data. If you'd rather it never did that, pin the workspace in Settings (see "Workspace lock").

What's the real difference between Free and Pro?

Free: 5 data extractions/day, 3 design generations/day, and only the free-eligible provider pool. Pro: 20/15 if you have both add-ons, otherwise 19/0 (data only) or 0/13 (design only), plus access to the extended provider pool. Business bumps it to 30/25 and unlocks the full pool.

The full table is above. Rate limits (per minute) are separate from daily quotas and don't change with tier in the current build.

Is my data used for training?

No. Sessions are stored per-user in MongoDB, keyed by your user id. The semantic cache key is derived from your prompt, workspace, task type, and the last two turns of your own conversation — it does not cross users.

When a provider is called, the request goes directly from our server to that provider. We don't insert a middle-man training layer, and we don't send your history to a provider that isn't handling your request.

What is the "Twin Engine" and why does it matter?

The Twin Engine is a local inference engine (core.twin_engine) that takes over when every remote provider has failed — all circuit breakers open, no keys configured, or TTFT thresholds tripped on the fallback chain.

If the engine itself isn't available (weights not loaded, host out of memory), the pipeline falls back to a stub response that is explicitly marked [stub] or {"_stub": true}. Downstream code treats that as a hard failure and surfaces it — it never renders as a normal answer.
